# Releasing rocker

Every push to `main` releases a new version. Nobody bumps the version or creates tags by hand.

## How a release happens

1. A push to `main` starts `.github/workflows/auto-release.yml`.
2. git-cliff (configured in `cliff.toml`) derives the next version from the commit messages since the latest `vX.Y.Z` tag:

   | Commits since the last tag | While 0.x | From 1.0.0 on |
   |---|---|---|
   | breaking (`feat!:`, `fix!:`, `BREAKING CHANGE:` footer) | minor | major |
   | `feat:` | minor | minor |
   | anything else, including non-conventional messages | patch | patch |

3. The workflow sets the version in `Cargo.toml` and `Cargo.lock`, regenerates `CHANGELOG.md`, commits `chore(release): vX.Y.Z` to `main` as `github-actions[bot]`, tags it, and pushes both.
4. It then dispatches `.github/workflows/release.yml` (generated by dist) for the tag. That workflow:
   - builds the four targets
   - creates the GitHub Release, using the version's `CHANGELOG.md` section as its notes
   - updates the formula in `ds82/homebrew-tap`
   - publishes `rocker-tui` to crates.io (`.github/workflows/publish-crates.yml`)

Pull requests against `main` show the version and changelog that merging would release in the job summary of "Auto release". Nothing is published from a PR.

Each push to `main` publishes a crates.io version, and those can never be deleted. To release several changes as one version, collect them on a branch and merge it in one push.

## One-time setup

Do this before the first merge to `main` that contains the release workflows, because that merge releases `v0.1.0` right away.

- [ ] Create the public repo `ds82/homebrew-tap` (empty, with a README is fine).
- [ ] Create a fine-grained GitHub token with **Contents: Read and write** access to `ds82/homebrew-tap` only. Store it as the Actions secret `HOMEBREW_TAP_TOKEN` in `ds82/rocker`:
  ```sh
  gh secret set HOMEBREW_TAP_TOKEN -R ds82/rocker
  ```
- [ ] Create a crates.io API token with the `publish-new` and `publish-update` scopes. Store it as `CARGO_REGISTRY_TOKEN`:
  ```sh
  gh secret set CARGO_REGISTRY_TOKEN -R ds82/rocker
  ```
  The first release claims the crate name `rocker-tui` for the account that owns this token.
- [ ] Check:
  ```sh
  gh secret list -R ds82/rocker      # shows both secrets
  gh repo view ds82/homebrew-tap
  ```

## Choosing the version yourself

To release a specific version, for example to go to 1.0.0, run the workflow by hand:

```sh
gh workflow run auto-release.yml -R ds82/rocker -f version=1.0.0
```

This works even when there are no new commits. Later pushes count from the new tag.

## Pausing releases

```sh
gh workflow disable auto-release.yml -R ds82/rocker   # pushes to main no longer release
gh workflow enable auto-release.yml -R ds82/rocker    # the next push releases everything since the last tag
```

## When something fails

- **"Auto release" failed before pushing**: nothing was tagged or published. This usually happens when another push landed during the run, so the atomic push was rejected. The next push to `main` releases all the changes since the last tag. To release right away, re-run the failed run.
- **`release.yml` failed after tagging**: the tag and the release commit exist. Re-run the failed jobs from the Actions tab. dist keeps the build artifacts, so re-running a publish job doesn't rebuild. To start the whole release again for the tag:
  ```sh
  gh workflow run release.yml -R ds82/rocker --ref vX.Y.Z -f tag=vX.Y.Z
  ```
  If the build itself is broken at that tag, push a fix. The fix releases the next version, and the broken tag stays without a GitHub Release.
- **The bot's push to `main` is rejected by branch protection or a ruleset**: add `github-actions` as a bypass actor for the rule (Settings → Rules), or switch the workflow to a GitHub App token that is allowed to bypass it.

## Rolling back a release

1. Delete the GitHub Release: `gh release delete vX.Y.Z -R ds82/rocker`.
2. Revert the formula commit in `ds82/homebrew-tap`.
3. Yank the crate version: `cargo yank --version X.Y.Z rocker-tui`. A yanked version stays visible but new installs won't resolve it.
4. **Keep the tag.** Versioning counts from it. Without the tag, the next run computes the yanked version again, and crates.io refuses to publish a version it already has.
5. Push the fix. It releases the next version.

## Changing the release workflows

- `release.yml` is generated by dist. Don't edit it by hand. Change `dist-workspace.toml`, then run `dist generate` (dist 0.33.0, from <https://github.com/axodotdev/cargo-dist/releases>). `dist generate --check` tells you whether the committed workflow is up to date.
- `auto-release.yml`, `publish-crates.yml` and `cliff.toml` are maintained by hand.
- Downloaded macOS binaries aren't signed or notarised. Homebrew and cargo-binstall installs are unaffected; direct downloads need `xattr -d com.apple.quarantine ./rocker`.
